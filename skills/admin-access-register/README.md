**Admin Access Register** - an admin access register records who holds administrative rights on each system, who the backup is, and when it was last reviewed. Instead of a spreadsheet only one person understands, each admin right becomes a row with a named owner, a status and a review rhythm. 22 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per admin right, 22 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 22 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `System or Tool`; `Category`; `Main Admin`; `Backup Admin`.
- `Department`; `Access Level`; `Number of Admin Users`; `Billing Owner`.
- Plus 14 more: `Plan`, `Seats`, `Renewal Date`, `Company Owned Account`, `Shared Login`, `Password Manager Entry` and 8 more.

Field types break down as 1 auto ID, 8 text, 1 long text, 4 select, 3 checkbox, 2 number and 3 date. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Admin rights accumulate: the person who set the tool up years ago is still an admin.

That is the argument for admin access register: privileged accounts are the ones that matter after someone leaves. Naming an owner per account is what makes removal possible.

Three things break at once without it. Nobody can answer "show me every admin right we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per admin right fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** grant, change or revoke access on any system.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many admin accounts exist?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - keep one row per named admin account with a system, an owner and a last-reviewed date. Shared logins are the first thing to fix.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: System listed → Admin account → Owner and approver → Periodic review → Removal

  system_or_tool VARCHAR(255),

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

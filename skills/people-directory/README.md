**People Directory** - a people directory is the one record per person that every other system links to, holding role, department, manager and contact details. Instead of a spreadsheet only one person understands, each person becomes a row with a named owner, a status and a review rhythm. 28 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per person, 28 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 28 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Full Name`; `Annual CTC`; `Currency`; `Date of Birth`.
- `Department`; `Email`; `Accounts`; `Emergency Contact`.
- Plus 20 more: `Emergency Phone`, `Employee ID`, `Employment Type`, `End Date`, `Grade Level`, `KPIs` and 14 more.

Field types break down as 1 auto ID, 15 text, 1 long text, 4 select, 1 currency, 3 date, 1 email and 2 web link. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Three spreadsheets hold three different phone numbers for the same person.

That is the argument for people directory: a people directory is the root record. If it is wrong, leave, assets, payroll and reviews are all wrong, so it is worth doing properly once.

Three things break at once without it. Nobody can answer "show me every person we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per person fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A starter-tier system: most small teams need it from day one.

**What it does not do:** hold payroll, tax or banking data. It references those, it does not own them.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many people are in the company today?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - one person record per human, with the sensitive fields separated out. Most modules should link to it, not duplicate it.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Joiner → Person record → Links to other modules → Change → Exit record

## Frequently asked questions

### What is the difference between people directory and a spreadsheet?

A spreadsheet is a container. People Directory is a defined set of 28 fields, a known owner and a stated review rhythm, which is what makes the data trustworthy. The skill emits the same field list as CSV, SQL and JSON Schema so the structure survives the move out of the sheet.

### What fields does a people directory system usually include?

At minimum Full Name, Annual CTC, Currency, Date of Birth. A complete version also covers Department, Email, Accounts, Emergency Contact. This template ships all 28, with types fixed rather than guessed.

### Do I need people directory if my team is small?

Yes - a starter-tier system, and most small teams need it from day one. The deciding question is not headcount, it is whether anyone can answer "show me every person we have" without checking with a person first.

## SQL reference

```sql
CREATE TABLE people_directory (
  full_name VARCHAR(255),
  annual_ctc NUMERIC(14,2) NOT NULL,
  currency VARCHAR(255),
  date_of_birth DATE NOT NULL,
  department VARCHAR(255),
  email VARCHAR(255),
  accounts VARCHAR(255),
  emergency_contact VARCHAR(255),
  emergency_phone VARCHAR(255),
  employee_id SERIAL PRIMARY KEY,
  employment_type VARCHAR(100) NOT NULL,
  end_date DATE NOT NULL,
  grade_level VARCHAR(100) NOT NULL,
  kpis VARCHAR(255),
  job_title VARCHAR(255),
  access_role VARCHAR(255),
  linkedin TEXT,
  manager VARCHAR(255),
  nationality VARCHAR(255),
  notes TEXT,
  phone VARCHAR(255),
  probation_status VARCHAR(100) NOT NULL,
  profile_photo_url TEXT,
  skills VARCHAR(255),
  start_date DATE NOT NULL,

  time_zone VARCHAR(255),

CREATE INDEX idx_people_directory_status ON people_directory (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

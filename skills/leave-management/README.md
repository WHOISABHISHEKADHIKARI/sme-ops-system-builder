**Leave Management** - a leave management system records each leave request with its dates, its approval and the balance it draws down, so cover is known in advance. Instead of a spreadsheet only one person understands, each leave request becomes a row with a named owner, a status and a review rhythm. 17 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per leave request, 17 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 17 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Leave Request`; `Annual Leave Balance`; `Approver`; `Days Requested`.
- `Department`; `Emergency Contact`; `Employee Name`; `End Date`.
- Plus 9 more: `Handover Notes`, `Leave ID`, `Leave Type`, `Manager`, `Notes`, `Reason` and 3 more.

Field types break down as 1 auto ID, 7 text, 2 long text, 2 select, 3 number and 2 date. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Leave balances live in one spreadsheet and the requests in another, so the balance is wrong by the time anyone checks it.

That is the argument for leave management: leave records go stale when balances and requests live apart. One place for both, with an approval state, keeps them consistent.

Three things break at once without it. Nobody can answer "show me every leave request we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per leave request fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A starter-tier system: most small teams need it from day one.

**What it does not do:** calculate country-specific leave entitlement or accrual rules.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many people need leave tracking?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - keep leave in the tool people already use and add the missing approval and balance steps, not a new system.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Request → Manager approval → Calendar entry → Balance update → Report

## Frequently asked questions

### What is the difference between leave management and a spreadsheet?

A spreadsheet is a container. Leave Management is a defined set of 17 fields, a known owner and a stated review rhythm, which is what makes the data trustworthy. The skill emits the same field list as CSV, SQL and JSON Schema so the structure survives the move out of the sheet.

### What fields does a leave management system usually include?

At minimum Leave Request, Annual Leave Balance, Approver, Days Requested. A complete version also covers Department, Emergency Contact, Employee Name, End Date. This template ships all 17, with types fixed rather than guessed.

### Do I need leave management if my team is small?

Yes - a starter-tier system, and most small teams need it from day one. The deciding question is not headcount, it is whether anyone can answer "show me every leave request we have" without checking with a person first.

### What does this system not do?

Leave Management touches decisions with legal, financial or employment consequences. ## SQL reference

```sql
CREATE TABLE leave_management (
  leave_request VARCHAR(255),
  annual_leave_balance NUMERIC NOT NULL,
  approver VARCHAR(255),
  days_requested NUMERIC NOT NULL,
  department VARCHAR(255),
  emergency_contact VARCHAR(255),
  employee_name VARCHAR(255),
  end_date DATE NOT NULL,
  handover_notes TEXT,
  leave_id SERIAL PRIMARY KEY,
  leave_type VARCHAR(100) NOT NULL,
  manager VARCHAR(255),
  notes TEXT,
  reason VARCHAR(255),
  sick_leave_balance NUMERIC NOT NULL,
  start_date DATE NOT NULL,
  status VARCHAR(100) NOT NULL,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_leave_management_status ON leave_management (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

## What it is

The page register: structure, on-page SEO, schema, NAP and performance targets

## When to use it

- build a website, set up a website, website plan
- page structure, sitemap, site map, information architecture
- "we have a website but nobody finds us"
- on-page SEO, meta titles, meta descriptions, headings
- structured data, schema, LocalBusiness, Service, FAQ
- Core Web Vitals, page speed, mobile
- NAP on the website, local signals, Google Search Console

## How it starts

Opens with one question, then asks only what is still missing - one per message.

> **Q:** What is the business called, and what does one line of it actually do?

- **Business** - Name, address, phone, services, service area? / Do customers visit a location, or is it a service-area business? / One location or several?
- **Current** - Is there a site today, and on what - WordPress, Shopify, Wix, Squarespace, a builder, or hand-built? / Who can publish a page? / Is there a developer or is it self-serve?
- **Customers** - What are the three questions a customer asks before they buy? / What do they search for? / Do they compare, or just want the nearest option?
- **Proof** - Any reviews, ratings, certifications, case studies or photos that can be shown? / Is there a team, a location, a process worth showing?
- **Outcome** - What is the site's job - calls, enquiries, bookings, direct sales, or just credibility? / Is there a phone number or WhatsApp that must be reachable in one tap?

**Recommended approach:** Five to eight pages, one per service and one per place, plus home, about, contact and a service-area page. Every service gets its own page with its own intent, its own NAP block and `LocalBusiness` or `Service` structured data. Mobile-first, fast, one clear call to action per page, and a review widget on the pages that earn trust. No blog unless someone will actually write it.

**Workflow:** Services and areas listed → Page map agreed → Search term and intent settled per page → NAP block placed → Structured data added → Titles, descriptions and headings written → Mobile and Core Web Vitals verified → Search Console and sitemap connected → Launched and submitted

Artifacts are built only after the user asks for them.

## SQL setup

```sql
-- Engine assumption: PostgreSQL. For another engine use the engine's auto-increment
-- equivalent and keep the rest portable.
CREATE TABLE website_page (
  id BIGINT PRIMARY KEY,
  page_url TEXT NOT NULL,
  page_title VARCHAR(255) NOT NULL,
  meta_description VARCHAR(500) NOT NULL,
  primary_keyword VARCHAR(255) NOT NULL,
  secondary_keywords TEXT,
  search_intent VARCHAR(100) NOT NULL,
  h1 VARCHAR(255) NOT NULL,
  nap_block_present BOOLEAN NOT NULL,
  schema_type VARCHAR(100) NOT NULL,
  canonical_url TEXT NOT NULL,
  indexable BOOLEAN NOT NULL,
  sitemap_included BOOLEAN NOT NULL,
  image_alt_text_rule VARCHAR(255) NOT NULL,
  target_device VARCHAR(50) NOT NULL,
  core_web_vitals_target VARCHAR(100) NOT NULL,
  build_platform VARCHAR(100),
  https BOOLEAN NOT NULL,
  mobile_first BOOLEAN NOT NULL,
  structured_data_valid BOOLEAN NOT NULL,
  owner VARCHAR(255),
  review_date DATE,
  status VARCHAR(50) NOT NULL,
  notes TEXT,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  CONSTRAINT website_page_intent CHECK (search_intent IN ('Informational','Commercial investigation','Transactional','Navigational','Local intent')),
  CONSTRAINT website_page_status CHECK (status IN ('Planned','In build','In review','Live','Needs update','Retired'))
);

CREATE INDEX idx_website_page_status ON website_page (status);
CREATE INDEX idx_website_page_intent ON website_page (search_intent);
```

## Frequently asked questions

### What is the difference between a website project and a page register?

A project ends when the site launches. A register keeps working afterwards, because pages get added, renamed and quietly lose their metadata. This is a defined set of 24 fields with a named owner and a review trigger, and the same 24 fields are emitted as CSV, SQL, JSON Schema and a Notion mapping, so a page cannot be considered done without its SEO fields filled in.

### What fields does a page register usually include?

At minimum Page ID, Page URL, Page Title and Meta Description. A register that holds up in search also needs Primary and Secondary Keywords, Search Intent and H1 so the page has one job; Canonical URL, Indexable and Sitemap Included so the indexing decisions are explicit rather than defaults; and NAP Block Present and Core Web Vitals targets, which are the two things small-business sites get wrong most often. This template ships all 24.

### Do I need a page register for a five-page site?

Yes - five pages is small enough to hold in your head and large enough that you will forget. The deciding question is whether you could list every page, its one job, and whether it is meant to be indexed, without opening the site.

### What does this system not do?

It ships an empty template, and it does not:
- build, host or publish the site.
- write the copy. It records the title, description and H1 so they are decided.
- measure Core Web Vitals. The targets are recorded; a real measurement tool reports the actual numbers.
- do keyword research. Primary and Secondary Keywords record the decision you reached.

### How does it fit with other systems?

It is the web end of the brand and local-search set. `gbp-local-seo-intent` targets the searches a profile should catch, `seo-directory-backlinks` the citations that point here, `linktree-link-hub` the bio links, and `design-theme-guide` the colour and type decisions behind the pages. NAP must match across all of them.

## Troubleshooting

- Columns show as Text after import - expected, apply the mapping table.
- Dates sort as text - convert the column to Date after import.
- A relation column stays empty - the target has to exist first.

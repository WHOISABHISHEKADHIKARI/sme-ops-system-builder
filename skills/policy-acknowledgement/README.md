**Policy Acknowledgement** - a policy acknowledgement record proves who has read and signed which version of a policy, and on what date. Instead of a spreadsheet only one person understands, each acknowledgement becomes a row with a named owner, a status and a review rhythm. 12 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per acknowledgement, 12 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 12 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Acknowledgement`; `Employee Name`; `Policy`; `Policy Version`.
- `Sent Date`; `Due Date`; `Acknowledged Date`; `Acknowledged`.
- Plus 4 more: `Days Overdue`, `Reminder Sent`, `Status`, `Acknowledgement ID`.

Field types break down as 1 auto ID, 4 text, 1 select, 2 checkbox, 1 number and 3 date. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

When a policy dispute appears, nobody can say who actually signed it or which version they saw.

That is the argument for policy acknowledgement: the failure mode is not missing policies, it is not knowing who has read the current version. Tracking by version fixes that.

Three things break at once without it. Nobody can answer "show me every acknowledgement we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per acknowledgement fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A starter-tier system: most small teams need it from day one.

**What it does not do:** host documents or capture legally binding e-signatures.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many policies need to be signed?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - issue the policy once, then track acknowledgement per person per version. A shared sign-off sheet beats individual emails.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Policy issue → Assign to people → Reminder → Sign-off record → Overdue report

## SQL reference

```sql
CREATE TABLE policy_acknowledgement (
  acknowledgement VARCHAR(255),
  employee_name VARCHAR(255),
  policy VARCHAR(255),
  policy_version VARCHAR(255),
  sent_date DATE NOT NULL,
  due_date DATE NOT NULL,
  acknowledged_date DATE NOT NULL,
  acknowledged BOOLEAN NOT NULL,
  days_overdue NUMERIC NOT NULL,
  reminder_sent BOOLEAN NOT NULL,
  status VARCHAR(100) NOT NULL,
  acknowledgement_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_policy_acknowledgement_status ON policy_acknowledgement (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

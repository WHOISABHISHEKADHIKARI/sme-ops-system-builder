**Salary Benchmarking** - salary benchmarking records what comparable roles pay in your market, so pay decisions rest on evidence rather than on whoever was hired last. Instead of a spreadsheet only one person understands, each benchmark becomes a row with a named owner, a status and a review rhythm. 13 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per benchmark, 13 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 13 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Role Title`; `Benchmark ID`; `Currency`; `Data Source`.
- `Department`; `Grade Level`; `Internal Max`; `Internal Min`.
- Plus 5 more: `Last Updated`, `Market Max`, `Market Median`, `Market Min`, `Notes`.

Field types break down as 1 auto ID, 4 text, 1 long text, 1 select, 5 currency and 1 date. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Pay levels drift by department and nobody notices until someone leaves over it.

That is the argument for salary benchmarking: benchmarking everything at once never finishes. Three hard-to-fill roles tell you more than fifty that are already correctly paid.

Three things break at once without it. Nobody can answer "show me every benchmark we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per benchmark fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A scale-tier system: build it when the business already runs on its own data rather than around it.

**What it does not do:** provide market data. Pay for the benchmark source separately.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** Which roles need benchmarking?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - benchmark the roles that are hardest to fill first, and store market range beside internal band so the gap is visible.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: Role list → Market data → Internal band → Gap analysis → Band decision

## Frequently asked questions

### What is the difference between salary benchmarking and a spreadsheet?

A spreadsheet is a container. Salary Benchmarking is a defined set of 13 fields, a known owner and a stated review rhythm, which is what makes the data trustworthy. The skill emits the same field list as CSV, SQL and JSON Schema so the structure survives the move out of the sheet.

### What fields does a salary benchmarking system usually include?

At minimum Role Title, Benchmark ID, Currency, Data Source. A complete version also covers Department, Grade Level, Internal Max, Internal Min. This template ships all 13, with types fixed rather than guessed.

## SQL reference

```sql
CREATE TABLE salary_benchmarking (
  role_title VARCHAR(255),
  benchmark_id SERIAL PRIMARY KEY,
  currency VARCHAR(255),
  data_source VARCHAR(255),
  department VARCHAR(255),
  grade_level VARCHAR(100) NOT NULL,
  internal_max NUMERIC(14,2) NOT NULL,
  internal_min NUMERIC(14,2) NOT NULL,
  last_updated DATE NOT NULL,
  market_max NUMERIC(14,2) NOT NULL,
  market_median NUMERIC(14,2) NOT NULL,
  market_min NUMERIC(14,2) NOT NULL,
  notes TEXT,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

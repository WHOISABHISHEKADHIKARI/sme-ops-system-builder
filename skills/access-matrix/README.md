**Access Matrix** - an access matrix records, for every role, which systems and data that role may view or change. Instead of a spreadsheet only one person understands, each access row becomes a row with a named owner, a status and a review rhythm. 16 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per access row, 16 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 16 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Module`; `Module ID`; `Layer`; `SME Tier`.
- `Owner / CEO`; `Board`; `Finance`; `Tax`.
- Plus 8 more: `HR`, `IT & Admin`, `Department Head`, `Line Manager`, `Employee`, `Intern` and 2 more.

Field types break down as 1 auto ID, 13 text and 2 select. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Access is granted in the moment and never reviewed, so ex-employees and people who moved roles keep permissions nobody intended.

That is the argument for access matrix: access problems are rarely about storage. They are about nobody re-checking who still needs what, so a review cycle matters more than the matrix itself.

Three things break at once without it. Nobody can answer "show me every access row we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per access row fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** provision or revoke access. It only records who should have what.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many roles exist in the company?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - keep the matrix in the tool the team already reviews in, and treat it as a recurring review rather than a one-time document.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: Role list → System inventory → Access rows → Quarterly review → Removal

## Frequently asked questions

### What is the difference between access matrix and a spreadsheet?

A spreadsheet is a container. Access Matrix is a defined set of 16 fields, a known owner and a stated review rhythm, which is what makes the data trustworthy. The skill emits the same field list as CSV, SQL and JSON Schema so the structure survives the move out of the sheet.

### What fields does an access matrix system usually include?

At minimum Module, Module ID, Layer, SME Tier. A complete version also covers Owner / CEO, Board, Finance, Tax. This template ships all 16, with types fixed rather than guessed.

### Do I need access matrix if my team is small?

Usually yes, and earlier than people expect. Access Matrix is a growth-tier system. The deciding question is not headcount, it is whether anyone can answer "show me every access row we have" without checking with a person first.

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

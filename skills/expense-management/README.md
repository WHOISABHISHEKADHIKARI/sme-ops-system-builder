**Expense Management** - an expense system records each claim with its category, amount, receipt and approval, so reimbursement is a decision rather than an argument. Instead of a spreadsheet only one person understands, each expense claim becomes a row with a named owner, a status and a review rhythm. 18 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per expense claim, 18 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 18 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Expense Claim`; `Amount`; `Tax Amount`; `Approver`.
- `Approval Level`; `Category`; `Currency`; `Date of Expense`.
- Plus 10 more: `Department`, `Employee Name`, `Expense ID`, `Notes`, `Project/Cost Centre`, `Budget Line` and 4 more.

Field types break down as 1 auto ID, 7 text, 1 long text, 3 select, 1 checkbox, 2 currency and 3 date. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Receipts arrive by email and get matched to claims by whoever has the best memory.

That is the argument for expense management: most expense problems are missing receipts and unclear limits, both of which can be enforced at data entry rather than at approval.

Three things break at once without it. Nobody can answer "show me every expense claim we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per expense claim fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A starter-tier system: most small teams need it from day one.

**What it does not do:** pay anything or connect to a bank or accounting system.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** What is your expense approval limit?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - build a claim form that forces receipt and amount, then route by limit. Keep the finance reconciliation as a separate monthly step.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Claim submitted → Manager approval → Finance check → Reimbursement → Monthly reconciliation

## SQL reference

```sql
CREATE TABLE expense_management (
  expense_claim VARCHAR(255),
  amount NUMERIC(14,2) NOT NULL,
  tax_amount NUMERIC(14,2) NOT NULL,
  approver VARCHAR(255),
  approval_level VARCHAR(100) NOT NULL,
  category VARCHAR(100) NOT NULL,
  currency VARCHAR(255),
  date_of_expense DATE NOT NULL,
  department VARCHAR(255),
  employee_name VARCHAR(255),
  expense_id SERIAL PRIMARY KEY,
  notes TEXT,
  project_cost_centre VARCHAR(255),
  budget_line VARCHAR(255),
  receipt_attached BOOLEAN NOT NULL,
  reimbursement_date DATE NOT NULL,
  status VARCHAR(100) NOT NULL,
  submission_date DATE NOT NULL,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_expense_management_status ON expense_management (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

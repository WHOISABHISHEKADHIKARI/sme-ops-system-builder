## What it is

Physical counts against book quantities, differences investigated and authorised adjustments passed

## When to use it

- physical stock count
- stock variance investigation
- stock adjustment register
- inventory shrinkage tracker
- cycle count sheet

## How it starts

Opens with one question, then asks only what is still missing - one per message.

> **Q:** How many items do you hold, and when did you last count them physically?

- **Stock** - What do you hold? / Raw material, finished goods or both? / How many locations?
- **Count** - Full count or cycle count? / How often? / Who counts and who verifies?
- **Differences** - What gets investigated? / Who approves an adjustment? / Any threshold to escalate?
- **Current process** - Counted today at all? / Sheet or accounting package? / What gets missed?
- **Outcome** - What do you need? / A reconciliation record, a count sheet or both?

**Recommended approach:** One reconciliation record per item counted, carrying the book quantity, the physical quantity, the variance, the reason and the authorised adjustment, with the count sheet filed against the same record so the count can be repeated next time.

**Workflow:** Count planned → Items counted → Compared with books → Variance investigated → Adjustment authorised → Adjustment booked → Reconciliation filed

Artifacts are built only after the user asks for them.

```sql
CREATE TABLE inventory_stock_reconciliation (
  reconciliation_number VARCHAR(255),
  count_date DATE NOT NULL,
  item_code VARCHAR(255),
  item_name VARCHAR(255),
  category VARCHAR(100) NOT NULL,
  uom VARCHAR(100) NOT NULL,
  location_warehouse VARCHAR(255),
  book_quantity NUMERIC,
  physical_quantity NUMERIC,
  variance_quantity NUMERIC,
  unit_rate NUMERIC(14,2) NOT NULL,
  variance_value NUMERIC(14,2) NOT NULL,
  variance_reason VARCHAR(100) NOT NULL,
  damaged_quantity NUMERIC,
  expired_quantity NUMERIC,
  slow_moving_flag VARCHAR(100),
  unrecorded_purchases NUMERIC,
  unrecorded_issues NUMERIC,
  investigation_notes TEXT,
  adjustment_entry VARCHAR(255),
  adjustment_date DATE,
  approved_by VARCHAR(255),
  counted_by VARCHAR(255),
  verified_by VARCHAR(255),
  count_frequency VARCHAR(100) NOT NULL,
  status VARCHAR(100) NOT NULL,
```

## Troubleshooting

- Columns show as Text after import - expected, apply the mapping table.
- Relation column stays empty - the target database must exist first.
- Dates sort as text - convert the column to Date after import.
- Variance will not compute - physical quantity minus book quantity, valued at the unit
  rate on the same row.
- A row sits at `In progress` for weeks - the reason or the approver is missing; that is
  the gate, not a status problem.

## Frequently asked questions

### What is the difference between inventory stock reconciliation and a spreadsheet?

A spreadsheet holds a count and a total. Inventory / Stock Reconciliation is a defined set of 28 fields where the count, the book quantity, the variance, the reason and the approver all sit on one row, with a named counter and a named verifier beside them. The same fields are emitted as CSV, SQL, JSON Schema and a Notion mapping. A sheet tells you stock is short; this tells you who signed the write-off off and on what grounds.

### What fields does an inventory stock reconciliation system usually include?

At minimum Reconciliation Number, Count Date, Item Code, Book Quantity, Physical Quantity, Variance Quantity. A complete version also carries Variance Value, Variance Reason, Damaged Quantity, Expired Quantity, Unrecorded Purchases, Unrecorded Issues, Adjustment Entry, Adjustment Date, Approved By, Counted By, Verified By and Count Frequency, because a difference is only worth anything once someone has explained it and someone else has approved it. This template ships all 28.

### Do I need inventory stock reconciliation if my team is small?

Yes - a growth-tier system, and any team holding physical stock needs it before the first close rather than after the shrinkage has shown up in the accounts. The deciding question is whether anyone can answer "how much did we count last quarter, and who approved the difference" without checking with a person. Counting is periodic by design: monthly where volume or value is high, quarterly at minimum, and the frequency belongs in the record rather than in someone's memory.

### What does this system not do?

It ships an empty template and computes or posts nothing. It does not count the stock, value the inventory or post the journal entry - the variance arithmetic belongs to the accounting package. It cannot tell theft from a mis-pick from an unrecorded issue; that call belongs to a person who knows the operation, and the row only carries the reason they gave. It does not set the valuation method, the reorder point or the costing policy.

### How does it fit with other systems?

It links rather than duplicates. Related modules: `purchase-accounting`, `sales-accounting`, `day-book` and `expense-accounting`. Each keeps its own table and joins on an ID, so unrecorded purchases and unrecorded issues get traced back to the transaction that caused them instead of being netted off here, and damaged or expired stock has somewhere to land once it is written off. This table declares no relation fields of its own.

**Candidate Talent Pool** - a talent pool keeps past and possible candidates warm, with the role they fit, how they were sourced and when they were last in touch. Instead of a spreadsheet only one person understands, each candidate becomes a row with a named owner, a status and a review rhythm. 15 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per candidate, 15 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 15 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Candidate Name`; `Candidate ID`; `Department`; `Email`.
- `Experience (Years)`; `Last Contact`; `LinkedIn URL`; `Notes`.
- Plus 7 more: `Phone`, `Re-engage Date`, `Referred By`, `Skills`, `Source`, `Status` and 1 more.

Field types break down as 1 auto ID, 7 text, 1 long text, 1 select, 1 number, 2 date, 1 email and 1 web link. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Strong applicants are lost because nobody wrote their name down.

That is the argument for candidate talent pool: rejected candidates are the cheapest hiring source you have, and the most commonly thrown away. Consent and a re-engage date are what make it reusable.

Three things break at once without it. Nobody can answer "show me every candidate we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per candidate fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** source candidates or send outreach on your behalf.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** Which roles do you hire for?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - keep a warm pool with consent and a re-engage date. It is a contact list with a purpose, not a resume archive.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Candidate added → Consent → Re-engage date → Reminder → Reopen role

## SQL reference

```sql
CREATE TABLE candidate_talent_pool (
  candidate_name VARCHAR(255),
  candidate_id SERIAL PRIMARY KEY,
  department VARCHAR(255),
  email VARCHAR(255),
  experience_years NUMERIC NOT NULL,
  last_contact DATE NOT NULL,
  linkedin_url TEXT,
  notes TEXT,
  phone VARCHAR(255),
  re_engage_date DATE NOT NULL,
  referred_by VARCHAR(255),
  skills VARCHAR(255),
  source VARCHAR(255),
  status VARCHAR(100) NOT NULL,
  target_role VARCHAR(255),
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_candidate_talent_pool_status ON candidate_talent_pool (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

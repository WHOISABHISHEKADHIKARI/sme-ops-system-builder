**Spreadsheet Manual Build** hands you the field list you already agreed as a workbook
you can open and use. One sheet, a bold frozen header, an autofilter, one column per
confirmed field, and the number, date and currency formats applied where they belong. The
rows are yours to enter: this builds a register, not a demo, and it never invents a record
to fill the space.

## What is this

A helper, not a database. It owns no field list of all - the fields already exist, in
`leave-management`, `expense-management`, `tax-register` and the rest. This helper takes
the module's confirmed field list and lays it out as a sheet, so the column set cannot
drift from the schema the rest of the system is built on.

What you get:

- an **`.xlsx` workbook** when you ask for one, or a **UTF-8 CSV with a byte order mark**
  when that is enough, plus a note of which columns need which format
- one **sheet by default**, named `Register`, unless the confirmed workflow needs more
- a **bold, frozen, filtered header** and sensible column widths
- **data validation lists** for confirmed select fields, and only those
- **no rows at all** unless you ask for example rows

## Why we need this

Spreadsheets outlive the tools that made them, and a workbook that starts as a register
ends up carrying a dashboard nobody opens, a lookup sheet pointing at a sheet that was
renamed, and a formula nobody can explain.

The smallest useful workbook is the one that stays true. One sheet, one header, one
column per field, and the formats set correctly once, is a register a team can maintain
for years. Every tab added for looks is a second thing to keep in step, and the thing that
goes out of step is always the data.

Three failures show up early without this: dates stored as text and sorting
alphabetically, amounts with no number format so totals refuse to add up, and a status
column that accepts any word anyone types.

## Who this is for

Any stage, any size, whenever the working format is a spreadsheet - which is most small
teams, most of the time. Also useful when a module has confirmed a field list and you want
it as a file rather than as a schema.

**What it does not do:** decide which fields you need, compute anything, or connect to
anything.

## How it works

The skill runs context first. It identifies the intent - template, examples, fix, or
mapping - reuses everything the module already confirmed, and asks **one question per
message** only for what is still missing. Its opening question is:

> **Q:** Do you want `.xlsx` or CSV?

Only then does it recommend the smallest workbook, and builds after you ask:

1. **Identify intent** - template only, examples on request, a targeted fix, or a mapping.
2. **Ask what is missing** - one question per message, never re-asking what you or the
   module skill already said.
3. **Recommend one approach** - one sheet, one header, one column per field.
4. **Build only on request** - the `.xlsx`, or the CSV and its format note. Data only.

The intended workflow is: Field list confirmed → Columns and formats set → Header frozen
and filtered → (rows entered by you) → Reviewed

## How columns are formatted

| Field type | In the sheet |
|---|---|
| `id`, `title`, `text`, `email`, `phone` | Text |
| `long_text` | Text, wrapped |
| `number` | Number format |
| `currency` | Currency or Accounting, only where you named the currency |
| `percentage` | Percentage |
| `date` | Date format |
| `datetime` | Date and time |
| `checkbox` | TRUE/FALSE |
| `select` | Data validation list of the confirmed options |
| `url` | Hyperlink or Text |
| `relation` | A reference key, not a live link |

Two rules do most of the work. Money is a number with a format, never text and never a
currency symbol in the cell, because the currency is a fact you confirm rather than one a
template assumes. And a relation is a key in a cell: nothing in a spreadsheet makes it a
link, and no lookup is built unless you ask for that design.

## Frequently asked questions

### Do I need a spreadsheet if I have a database?

Not instead of one, usually alongside it. A schema decides what a system may hold; a
spreadsheet is what people fill in on Monday morning. This helper exists so the two agree
on the column set, not so one replaces the other.

### Why is the workbook empty?

Because you did not ask for rows, and a stray row is a record somebody has to delete
later - or worse, imports as real. Example rows are one request away, and when they arrive
they are obviously fake.

### Why do my dates sort as text?

Because the column holds text. A date format applied to text changes how it looks, not
what it is. Convert the column to a date, or re-export with dates as ISO `YYYY-MM-DD`.

### Can it add a dashboard or a chart?

Not unless the confirmed workflow needs one. Charts and dashboards are usually a request
for reassurance, and they rot quietly while the register they summarise stops being
updated. Ask explicitly and it will build what you asked for.

### What does this system not do?

- It formats a field list someone else confirmed. It never decides the schema.
- It computes nothing. A value the parent skill says belongs in accounting or tax
  software stays a value, and no Excel formula is written for it.
- It creates no automation, no integration and no synchronisation, and will not claim one.
- Data validation lists are a convenience: a pasted value can still get in.

### How does it fit with other systems?

It sits on top of them. Related modules: `sme-ops-system-builder`, `leave-management`,
`expense-management`. The workbook adds no storage of its own, so a schema change shows up
as a new column rather than a migration.

## Troubleshooting

- **Dates sort alphabetically** - the column is text. Convert it to a date.
- **Totals do not add up** - the amount column is text. Convert it to Number and set the
  format.
- **A currency symbol is in the cell** - that currency was assumed. Remove it and apply a
  currency format only where you named the currency.
- **A status column accepts any word** - data validation is a convenience, not a rule.
  Keep the confirmed list as the reference and correct the entry.
- **A relation column looks empty** - it holds a key, not a link. The link is made in the
  system that holds the target.

**Offer & Appointment** - an offer record captures the terms, the approvers and the decision behind each hire, so the paperwork matches what was agreed. Instead of a spreadsheet only one person understands, each offer becomes a row with a named owner, a status and a review rhythm. 18 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per offer, 18 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 18 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Offer Title`; `Candidate Name`; `Recruitment Record`; `Position`.
- `Department`; `Grade Level`; `Employment Type`; `Offered Salary`.
- Plus 10 more: `Currency`, `Offer Date`, `Offer Expiry`, `Joining Date`, `Probation Period (Days)`, `Approver` and 4 more.

Field types break down as 1 auto ID, 7 text, 1 long text, 3 select, 1 number, 1 currency, 3 date and 1 relation. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Offer terms get agreed in chat and reconstructed later from memory.

That is the argument for offer and appointment: offer data is the bridge between recruiting and payroll. Capturing it once, at offer stage, prevents re-keying at joining.

Three things break at once without it. Nobody can answer "show me every offer we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per offer fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** generate contracts or send legally binding documents.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many offers do you make a month?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - store the offer as a record with version, approver and expiry. The template is secondary; the record is what you lose today.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Approved offer → Offer sent → Candidate accepts → Record created → Onboarding started

## SQL reference

```sql
CREATE TABLE offer_appointment (
  offer_title VARCHAR(255),
  candidate_name VARCHAR(255),
  recruitment_record VARCHAR(255),  -- relation -> target record
  position VARCHAR(255),
  department VARCHAR(255),
  grade_level VARCHAR(100) NOT NULL,
  employment_type VARCHAR(100) NOT NULL,
  offered_salary NUMERIC(14,2) NOT NULL,
  currency VARCHAR(255),
  offer_date DATE NOT NULL,
  offer_expiry DATE NOT NULL,
  joining_date DATE NOT NULL,
  probation_period_days NUMERIC NOT NULL,
  approver VARCHAR(255),
  signed_via VARCHAR(255),
  status VARCHAR(100) NOT NULL,
  notes TEXT,
  offer_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_offer_appointment_status ON offer_appointment (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

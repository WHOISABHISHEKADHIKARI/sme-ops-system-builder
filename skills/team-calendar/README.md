**Team Calendar** - a team calendar gives one place for leave, holidays, training and company events, so availability is read from a single view. Instead of a spreadsheet only one person understands, each event becomes a row with a named owner, a status and a review rhythm. 13 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per event, 13 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 13 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Event`; `Event Type`; `Date`; `Start Time`.
- `End Time`; `Time Zone`; `Department`; `Attendees`.
- Plus 5 more: `Organizer`, `Source Module`, `Location or Link`, `Notes`, `Event ID`.

Field types break down as 1 auto ID, 8 text, 1 long text, 1 select, 1 date and 1 web link. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Leave sits in a spreadsheet and training in an inbox, so nobody actually knows who is free.

That is the argument for team calendar: two calendars is worse than one. If a shared calendar already exists, the useful output is a record of key events, not a scheduler.

Three things break at once without it. Nobody can answer "show me every event we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per event fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** create calendar events in Google or resolve scheduling conflicts.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** What should appear on the shared calendar?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - keep the calendar in the tool already used and make the database a thin index of it, not a second calendar.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Event created → Calendar entry → Attendance or RSVP → Reminder

## SQL reference

```sql
CREATE TABLE team_calendar (
  event VARCHAR(255),
  event_type VARCHAR(100) NOT NULL,
  date DATE NOT NULL,
  start_time VARCHAR(255),
  end_time VARCHAR(255),
  time_zone VARCHAR(255),
  department VARCHAR(255),
  attendees VARCHAR(255),
  organizer VARCHAR(255),
  source_module VARCHAR(255),
  location_or_link TEXT,
  notes TEXT,
  event_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

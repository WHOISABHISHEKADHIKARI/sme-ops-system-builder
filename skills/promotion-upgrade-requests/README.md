**Promotion & Upgrade Requests** - an upgrade request records a proposed promotion or salary change, the evidence behind it, the approvals and the effective date. Instead of a spreadsheet only one person understands, each upgrade request becomes a row with a named owner, a status and a review rhythm. 25 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per upgrade request, 25 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 25 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Request Title`; `Employee Name`; `Department`; `Request Type`.
- `Current Job Title`; `Current Grade`; `Requested Job Title`; `Requested Grade`.
- Plus 17 more: `Requested By`, `Justification`, `Linked Performance Review`, `OKR Score`, `Behaviour Score`, `Courses Completed` and 11 more.

Field types break down as 1 auto ID, 13 text, 2 select, 1 checkbox, 4 number, 2 currency, 1 date and 1 relation. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Pay and title changes are agreed in a meeting and never reconciled with the payroll record.

That is the argument for promotion and upgrade requests: promotion decisions drift when the request, the evidence and the decision live in different places. One record with a decision field fixes the trail.

Three things break at once without it. Nobody can answer "show me every upgrade request we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per upgrade request fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** decide promotions or change pay. It records and routes the request.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** Who can request a promotion?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - require a written request with evidence, route it by grade, and record the decision and effective date as one object.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: Request submitted → Criteria check → Approval → Decision → People and payroll update

## SQL reference

```sql
CREATE TABLE promotion_upgrade_requests (
  request_title VARCHAR(255),
  employee_name VARCHAR(255),
  department VARCHAR(255),
  request_type VARCHAR(100) NOT NULL,
  current_job_title VARCHAR(255),
  current_grade VARCHAR(255),

  courses_completed VARCHAR(255),
  time_in_role_months NUMERIC NOT NULL,
  criteria_met BOOLEAN NOT NULL,
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

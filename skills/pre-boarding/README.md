**Pre-boarding** - pre-boarding records what has to happen before a new joiner’s first day, so equipment, accounts and access are ready rather than promised. Instead of a spreadsheet only one person understands, each pre-boarding task becomes a row with a named owner, a status and a review rhythm. 14 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per pre-boarding task, 14 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 14 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Pre-boarding Task`; `Employee Name`; `Department`; `Owner`.
- `Category`; `Joining Date`; `Due Date`; `Documents Received`.
- Plus 6 more: `Laptop Ready`, `Email Created`, `Account Record`, `Status`, `Notes`, `Pre-board ID`.

Field types break down as 1 auto ID, 5 text, 1 long text, 2 select, 3 checkbox and 2 date. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Day one starts with a new joiner waiting for a laptop that was ordered on day three.

That is the argument for pre-boarding: pre-boarding stalls on the last few days, so a checklist tied to a date is worth more than a task list. Unfinished items are the signal.

Three things break at once without it. Nobody can answer "show me every pre-boarding task we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per pre-boarding task fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** order equipment, provision accounts or send anything on your behalf.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** When does the new joiner start?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - build a dated checklist that runs backwards from the start date, and mark each item done rather than tracking tasks generically.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: Joiner added → Checklist generated → Items due by date → Day-one handover

## SQL reference

```sql
CREATE TABLE pre_boarding (
  pre_boarding_task VARCHAR(255),
  employee_name VARCHAR(255),
  department VARCHAR(255),
  owner VARCHAR(255),
  category VARCHAR(100) NOT NULL,
  joining_date DATE NOT NULL,
  due_date DATE NOT NULL,
  documents_received BOOLEAN NOT NULL,
  laptop_ready BOOLEAN NOT NULL,
  email_created BOOLEAN NOT NULL,
  account_record VARCHAR(255),
  status VARCHAR(100) NOT NULL,
  notes TEXT,
  pre_board_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_pre_boarding_status ON pre_boarding (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

**Company Email & Accounts** - a company accounts register records every work email, shared inbox and tool login a person holds, with its owner and its renewal date. Instead of a spreadsheet only one person understands, each account becomes a row with a named owner, a status and a review rhythm. 22 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per account, 22 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 22 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Account Record`; `Employee Name`; `Department`; `Account Type`.
- `Work Email`; `Aliases`; `Email Groups`; `Tool or System`.
- Plus 14 more: `Licence Type`, `Licence Cost`, `Currency`, `Created Date`, `Created By`, `Two Factor On` and 8 more.

Field types break down as 1 auto ID, 9 text, 1 long text, 3 select, 3 checkbox, 1 currency, 3 date and 1 email. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Tool logins get created in a hurry and never removed, so ownership of critical systems stays unclear.

That is the argument for company email and accounts: account sprawl is a security problem, not an admin problem. One register per person, with join and leave dates, is the whole fix.

Three things break at once without it. Nobody can answer "show me every account we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per account fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A starter-tier system: most small teams need it from day one.

**What it does not do:** create or delete accounts. It only records what should exist.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** Which tools need an account per person?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - build an account register tied to people records, then provision and remove from that one list.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Joiner → Create accounts → Assign tools → Leave → Remove access → Log

CREATE TABLE company_email_accounts (
  account_record VARCHAR(255),
  employee_name VARCHAR(255),
  department VARCHAR(255),
  account_type VARCHAR(100) NOT NULL,

  aliases VARCHAR(255),

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

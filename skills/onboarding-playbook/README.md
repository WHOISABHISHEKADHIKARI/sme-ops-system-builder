**Onboarding Playbook** - an onboarding playbook turns joining the company into a dated checklist with named owners, rather than a list of things new joiners are expected to know. Instead of a spreadsheet only one person understands, each onboarding step becomes a row with a named owner, a status and a review rhythm. 9 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per onboarding step, 9 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 9 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Onboarding Step`; `Phase`; `Order`; `Department`.
- `Owner`; `Linked SOP`; `Required`; `Notes`.
- Plus 1 more: `Step ID`.

Field types break down as 1 auto ID, 4 text, 1 long text, 1 checkbox, 1 number and 1 relation. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Every new joiner gets a different first month depending on who happens to be around.

That is the argument for onboarding playbook: onboarding plans fail when they are per-person documents. One plan with day offsets is reusable and keeps a 30 percent no-show from being missed.

Three things break at once without it. Nobody can answer "show me every onboarding step we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per onboarding step fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** chase tasks or notify owners on their own.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** When does a new joiner start?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - build a checklist with an owner and a due offset from the joining date, so the same plan applies to every new joiner.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: Offer accepted → Pre-boarding → Day one → Week one → 30, 60, 90 day

## Frequently asked questions

### What is the difference between onboarding playbook and a spreadsheet?

A spreadsheet is a container. Onboarding Playbook is a defined set of 9 fields, a known owner and a stated review rhythm, which is what makes the data trustworthy. The skill emits the same field list as CSV, SQL and JSON Schema so the structure survives the move out of the sheet.

### What fields does an onboarding playbook system usually include?

At minimum Onboarding Step, Phase, Order, Department. A complete version also covers Owner, Linked SOP, Required, Notes. This template ships all 9, with types fixed rather than guessed.

### Do I need onboarding playbook if my team is small?

Usually yes, and earlier than people expect. Onboarding Playbook is a growth-tier system. The deciding question is not headcount, it is whether anyone can answer "show me every onboarding step we have" without checking with a person first.

## SQL reference

```sql
CREATE TABLE onboarding_playbook (
  onboarding_step VARCHAR(255),
  phase VARCHAR(255),
  sort_order NUMERIC NOT NULL,
  department VARCHAR(255),
  owner VARCHAR(255),
  linked_sop VARCHAR(255),  -- relation -> target record
  required BOOLEAN NOT NULL,
  notes TEXT,
  step_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

**OKR System** - an OKR system records objectives and the key results that prove them, with owners and confidence, so priorities are compared rather than restated. Instead of a spreadsheet only one person understands, each objective becomes a row with a named owner, a status and a review rhythm. 20 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per objective, 20 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 20 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Objective`; `Department`; `End Date`; `KR1 Progress %`.
- `KR2 Progress %`; `KR3 Progress %`; `Key Result 1`; `Key Result 2`.
- Plus 12 more: `Key Result 3`, `Last Updated`, `Level`, `Notes`, `OKR ID`, `Owner` and 6 more.

Field types break down as 1 auto ID, 8 text, 1 long text, 2 select, 4 number, 3 date and 1 relation. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Quarterly goals are agreed in a meeting and forgotten by the second week.

That is the argument for OKR system: oKRs fail when objectives have no key results or no review date. Enforce both at creation rather than reviewing for them later.

Three things break at once without it. Nobody can answer "show me every objective we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per objective fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** assess individual performance or connect to compensation.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many objectives are you setting this quarter?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - cascade company to team to person, and review progress on a fixed cadence. Three key results per objective is the practical limit.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Objective → Key results → Owner → Progress update → Review → Close

## Frequently asked questions

### What is the difference between OKR system and a spreadsheet?

A spreadsheet is a container. OKR System is a defined set of 20 fields, a known owner and a stated review rhythm, which is what makes the data trustworthy. The skill emits the same field list as CSV, SQL and JSON Schema so the structure survives the move out of the sheet.

### What fields does an OKR system usually include?

At minimum Objective, Department, End Date, KR1 Progress %. A complete version also covers KR2 Progress %, KR3 Progress %, Key Result 1, Key Result 2. This template ships all 20, with types fixed rather than guessed.

### Do I need OKR system if my team is small?

Usually yes, and earlier than people expect. OKR System is a growth-tier system. The deciding question is not headcount, it is whether anyone can answer "show me every objective we have" without checking with a person first.

### What does this system not do?

- Empty template only. It does not compute payroll, tax, leave balances or KPIs.

## SQL reference

```sql
CREATE TABLE okr_system (
  objective VARCHAR(255),
  department VARCHAR(255),
  end_date DATE NOT NULL,
  kr1_progress NUMERIC NOT NULL,
  kr2_progress NUMERIC NOT NULL,
  kr3_progress NUMERIC NOT NULL,
  key_result_1 VARCHAR(255),
  key_result_2 VARCHAR(255),
  key_result_3 VARCHAR(255),
  last_updated DATE NOT NULL,
  level VARCHAR(100) NOT NULL,
  notes TEXT,
  okr_id SERIAL PRIMARY KEY,
  owner VARCHAR(255),
  parent_okr VARCHAR(255),  -- relation -> target record
  progress NUMERIC NOT NULL,
  quarter VARCHAR(255),
  start_date DATE NOT NULL,
  status VARCHAR(100) NOT NULL,
  year VARCHAR(255),
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_okr_system_status ON okr_system (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

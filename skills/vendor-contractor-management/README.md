**Vendor & Contractor Management** - a vendor register records each supplier and contractor, their terms, their invoices and their renewal dates, in one place. Instead of a spreadsheet only one person understands, each vendor becomes a row with a named owner, a status and a review rhythm. 14 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per vendor, 14 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 14 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Vendor Name`; `Vendor Type`; `Services`; `Contact Person`.
- `Email`; `Phone`; `Department`; `Linked Contract`.
- Plus 6 more: `Contract Start`, `Contract End`, `Payment Terms`, `Rating`, `Status`, `Vendor ID`.

Field types break down as 1 auto ID, 6 text, 2 select, 1 number, 2 date, 1 email and 1 relation. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Suppliers get managed through whichever relationship is strongest, rather than through a record.

That is the argument for vendor and contractor management: vendor risk concentrates in the few vendors with access. Tag those and review them; the rest need a register, not a process.

Three things break at once without it. Nobody can answer "show me every vendor we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per vendor fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A scale-tier system: build it when the business already runs on its own data rather than around it.

**What it does not do:** assess vendors, sign anything or manage payments.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many vendors or contractors do you work with?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - one record per vendor with an owner, the renewal date and what they can access, and review the ones with data or system access more often.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: Vendor recorded → Owner assigned → Due diligence → Review → Renewed or ended

## SQL reference

```sql
CREATE TABLE vendor_contractor_management (
  vendor_name VARCHAR(255),
  vendor_type VARCHAR(100) NOT NULL,
  services VARCHAR(255),
  contact_person VARCHAR(255),
  email VARCHAR(255),
  phone VARCHAR(255),
  department VARCHAR(255),
  linked_contract VARCHAR(255),  -- relation -> target record
  contract_start DATE NOT NULL,
  contract_end DATE NOT NULL,
  payment_terms VARCHAR(255),
  rating NUMERIC NOT NULL,
  status VARCHAR(100) NOT NULL,
  vendor_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_vendor_contractor_management_status ON vendor_contractor_management (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

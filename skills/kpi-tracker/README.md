**KPI Tracker** - a KPI tracker records a measure, its target, its actual and its weight, so performance is compared against something agreed in advance. Instead of a spreadsheet only one person understands, each KPI becomes a row with a named owner, a status and a review rhythm. 18 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per KPI, 18 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 18 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `KPI Name`; `KPI Level`; `Department`; `Job Title`.
- `Employee Name`; `Linked OKR`; `Unit`; `Direction`.
- Plus 10 more: `Target`, `Actual`, `Achievement %`, `Weight %`, `Weighted Score`, `Period` and 4 more.

Field types break down as 1 auto ID, 9 text, 2 select, 5 number and 1 relation. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Performance is discussed from memory, and the measure being argued about changes between meetings.

That is the argument for KPI tracker: kPI trackers fail from volume, not from schema. Fewer metrics reviewed on a schedule beats a full scorecard nobody opens.

Three things break at once without it. Nobody can answer "show me every KPI we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per KPI fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** collect data automatically or connect to a source system.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** Which KPIs matter most?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - start with three to five metrics per level and a fixed review cadence. Weighting only matters when scores are compared across people.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: KPI definition → Target → Actual entry → Achievement → Review meeting

## SQL reference

```sql
CREATE TABLE kpi_tracker (
  kpi_name VARCHAR(255),
  kpi_level VARCHAR(100) NOT NULL,
  department VARCHAR(255),
  job_title VARCHAR(255),
  employee_name VARCHAR(255),
  linked_okr VARCHAR(255),  -- relation -> target record
  unit VARCHAR(255),
  direction VARCHAR(255),
  target NUMERIC NOT NULL,
  actual NUMERIC NOT NULL,
  achievement NUMERIC NOT NULL,
  weight NUMERIC NOT NULL,
  weighted_score NUMERIC NOT NULL,
  period VARCHAR(255),
  data_source VARCHAR(255),
  owner VARCHAR(255),
  status VARCHAR(100) NOT NULL,
  kpi_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_kpi_tracker_status ON kpi_tracker (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

**Budget & Cash Flow** - a budget and cash flow record compares budgeted and actual spend by department and month, and tracks money in and money out. Instead of a spreadsheet only one person understands, each budget line becomes a row with a named owner, a status and a review rhythm. 15 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per budget line, 15 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 15 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Budget Line`; `Line Type`; `Department`; `Category`.
- `Period`; `Fiscal Year`; `Budget Amount`; `Actual Amount`.
- Plus 7 more: `Variance`, `Used %`, `Linked Expenses`, `Owner`, `Status`, `Notes` and 1 more.

Field types break down as 1 auto ID, 5 text, 1 long text, 3 select, 1 number, 3 currency and 1 relation. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Spend is only known to be over budget once the month is closed.

That is the argument for budget and cash flow: cash flow fails from stale forecasts, not from a missing template. A monthly refresh of a small model beats a detailed annual plan nobody updates.

Three things break at once without it. Nobody can answer "show me every budget line we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per budget line fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** move money, book transactions or give financial advice.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How far ahead do you budget?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - build the budget once per year and the cash view monthly, and record the variance rather than rewriting the whole forecast.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: Budget set → Monthly actuals entered → Variance calculated → Cash position → Forecast revised

## SQL reference

```sql
CREATE TABLE budget_cash_flow (
  budget_line NUMERIC(14,2) NOT NULL,
  line_type VARCHAR(100) NOT NULL,
  department VARCHAR(255),
  category VARCHAR(100) NOT NULL,
  period VARCHAR(255),
  fiscal_year VARCHAR(255),
  budget_amount NUMERIC(14,2) NOT NULL,
  actual_amount NUMERIC(14,2) NOT NULL,
  variance VARCHAR(255),
  used NUMERIC NOT NULL,
  linked_expenses VARCHAR(255),  -- relation -> target record
  owner VARCHAR(255),
  status VARCHAR(100) NOT NULL,
  notes TEXT,
  budget_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_budget_cash_flow_status ON budget_cash_flow (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

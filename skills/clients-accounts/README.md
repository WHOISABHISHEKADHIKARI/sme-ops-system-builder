**Clients & Accounts** - a client register records each customer with its contacts, its payment terms and its outstanding balance, so who owes what is answerable. Instead of a spreadsheet only one person understands, each client becomes a row with a named owner, a status and a review rhythm. 21 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per client, 21 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 21 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Client Name`; `Client Type`; `Industry`; `Contact Person`.
- `Email`; `Phone`; `Billing Address`; `Tax ID`.
- Plus 13 more: `Currency`, `Tax Basis`, `Payment Terms (Days)`, `Account Manager`, `Projects`, `Invoices`, `Total Invoiced` and 6 more.

Field types break down as 1 auto ID, 11 text, 1 long text, 3 select, 1 number, 3 currency and 1 email. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

The client list lives in one person’s contacts app, and nobody else can see it.

That is the argument for clients and accounts: client records go stale when contact details change. A named owner and a next-action date keep the register usable.

Three things break at once without it. Nobody can answer "show me every client we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per client fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A starter-tier system: most small teams need it from day one.

**What it does not do:** contact clients, send invoices or manage the relationship for you.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many active clients do you have?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - one record per client with a named owner and next action, and keep activity notes on that record rather than in a separate log.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Client recorded → Owner assigned → Activity logged → Next action → Review

## SQL reference

```sql
CREATE TABLE clients_accounts (
  client_name VARCHAR(255),
  client_type VARCHAR(100) NOT NULL,
  industry VARCHAR(255),
  contact_person VARCHAR(255),
  email VARCHAR(255),
  phone VARCHAR(255),
  billing_address VARCHAR(255),
  tax_id VARCHAR(255),
  currency VARCHAR(255),
  payment_terms_days NUMERIC NOT NULL,
  account_manager VARCHAR(255),
  projects VARCHAR(255),
  invoices VARCHAR(255),
  total_invoiced NUMERIC(14,2) NOT NULL,
  total_paid NUMERIC(14,2) NOT NULL,
  outstanding NUMERIC(14,2) NOT NULL,
  client_portal_access VARCHAR(255),
  status VARCHAR(100) NOT NULL,
  notes TEXT,
  client_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_clients_accounts_status ON clients_accounts (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

**JSON Schema Manual** gives you the field list you already agreed as a validation
contract. One object schema, one property per confirmed field, `required` entries only
where the source marks them required, and `enum` values only where the business has
settled them. The damage from a schema is asymmetric: an omitted property passes data
nobody reviewed, while an invented `required` or `enum` rejects data that was perfectly
valid.

## What is this

A helper, not a database. The fields belong to `leave-management`,
`expense-management`, `invoice-billing` and the rest; this emits the module's confirmed
field list as a schema, so the property names in a payload are the names the system
already uses.

What you get:

- **draft 2020-12** `https://json-schema.org/draft/2020-12/schema`, or the version the
  consuming system already uses
- **one property per confirmed field**, the same names and order as the CSV, SQL and
  spreadsheet outputs
- **no guessed `required` entries** and **no invented `enum` values**
- **strictness only where the contract is closed** - one question, asked once
- no examples, and no instance data

## Why we need this

A schema is a promise about what a payload may contain, and every restriction in it
rejects real data. That asymmetry is the whole design rule.

The common failure is a schema written from intuition: every field marked required
because they obviously are, a status column with an `enum` copied from a starting set
rather than a settled taxonomy, `null` allowed everywhere so the type union is thorough.
The first week it is convenient. The first time a real record arrives with a status nobody
listed, the pipeline rejects it, and the fix is a code change to satisfy data that was
never wrong.

A schema cannot help here. It validates structure and nothing else: it will not check that
a client exists, that a total equals a sum, or that a due date follows an invoice date.
Anyone expecting that is reading enforcement into a document that contains none.

## Who this is for

Any stage, any size, whenever a payload has to be agreed before it is trusted: an internal
API, an import contract with another team, a generated form, or a file format someone
else will implement against you.

**What it does not do:** compute values, connect to anything, or decide which fields the
business needs.

## How it works

The skill runs context first. It identifies the intent - schema, review, fix, or advice -
reuses everything the module already confirmed, and asks **one question per message**
only for what is still missing. Its opening question is:

> **Q:** Should the schema reject unknown fields, or allow them?

Only then does it recommend the smallest contract, and emits the schema after you ask:

1. **Identify intent** - a schema, a review, a targeted fix, or advice.
2. **Ask what is missing** - one question per message, never re-asking what you or the
   module skill already said.
3. **Recommend one approach** - one object schema, no unconfirmed restrictions.
4. **Emit only on request** - the schema as data, with no wrapper.

The intended workflow is: Field list confirmed → Properties typed → Requiredness applied
from the source → (validated) → Published as the contract

## How field types map

| Field type | JSON Schema |
|---|---|
| `id` | `integer` or `string`, matching the confirmed source |
| `title`, `text`, `long_text`, `phone` | `string` |
| `number`, `currency`, `percentage` | `number` |
| `date` | `string`, `format: date` |
| `datetime` | `string`, `format: date-time` |
| `checkbox` | `boolean` |
| `select` | `string` |
| `multi_select` | `array` of `string` |
| `url` | `string`, `format: uri` |
| `email` | `string`, `format: email` |
| `relation` | `string` or `integer`, matching the reference key |
| `files` | `array` or `string`, only where the source defines it |

`format` is an annotation, not an enforcement. Many validators treat `email` and `date` as
advice, so a payload that validates may still be wrong - worth knowing before you build a
guarantee on top of it.

Paste this into Claude, ChatGPT, Gemini or Cursor to start the intake:

```
I need a JSON Schema for [database], from the fields we already agreed.

```

## Frequently asked questions

### Which fields should be required?

Only the ones the field list already marks required, or the ones you explicitly confirm.
Requiredness is not a matter of taste: marking a field required that the source may
legitimately leave empty turns a schema into a source of rejections. If the list does not
say, the field is optional until you say otherwise.

### Should I add `additionalProperties: false`?

Only where the contract is genuinely closed - you are the only writer, and extra fields
are a bug rather than someone else's future. Against a partner or a client, that single
line is the most common cause of a rejected payload. The skill asks once, and otherwise
follows the parent module's convention.

### Why are my status values not in an `enum`?

Because they are a starting set, not a settled taxonomy. An `enum` is a rejection waiting
to happen, and a value copied from a suggestion is not a value the business has agreed.
Where the options are open, the property stays a plain `string` and the notes say so.

### What about `null`?

Allow it only where the source distinguishes null from missing. For unknown or optional
data, omit the field rather than inventing null semantics - and note that a validator
accepting `null` where the data model has no such value is a rule nobody agreed to.

### Can the schema compute anything?

No. A calculated field appears as its data type and nothing more; the producing system
computes the value. Nor can it express cross-field rules - a due date after an invoice
date, a total equal to a sum - so nothing here will ever catch a payload that is
structurally perfect and factually wrong.

`expense-management`, `notion-manual-import`. Versioning and CI are the consuming
system's job, not this helper's.

## Troubleshooting

- **Payload rejected for an extra field** - `additionalProperties: false` on an open
  contract. Loosen it.
- **A real status value fails validation** - an `enum` copied from a starting set. Make
  the property a `string` until the taxonomy is settled.
- **Numbers arrive as strings** - quotes in the payload. Numeric fields take unquoted
  values.
- **A required field is missing** - it is not actually required in the source. Confirm it
  with the people who own the data before adding it.
- **A `date` that looks wrong passes validation** - `format` is advisory. Check the
  payload, not just the validator.
- **Validation passes and the data is still wrong** - expected. A schema checks structure.

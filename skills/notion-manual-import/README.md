**Notion Manual Import** is the unconnected path into Notion. Pick the module that owns
your schema, and this helper hands you a CSV with the exact field names, the property
mapping that turns the imported Text columns into real Notion types, the shortest import
click-path, and the list of things to verify afterwards. Nothing is connected, uploaded or
created for you: you do the import, this tells you exactly what to press and what to fix.

## What is this

A helper, not a database. It owns no table, because the field list already exists - in
`people-directory`, `leave-management`, `tax-register` and the rest. This page is about the
part that goes wrong: a CSV carries no types, so every column lands in Notion as Text, and
the import looks broken when it is not.

What you get, in the order you need it:

- a **CSV** whose header is the source module's field names, in the same order, empty
  unless you ask for examples
- a **property mapping** table: one row per column, the Notion type to convert it to, and
  what to do after import
- the **import steps**, described by action rather than by button name, because Notion's
  labels move between versions
- the **verification checklist** that turns "imported" into "correct"

## Why we need this

The connected path is better when it is available: the assistant creates the database and
the properties itself. Plenty of small teams cannot or will not go there - no admin rights,
no shared workspace, a client who does not want their records in an assistant's hands, or
simply a preference for doing it themselves.

That is not a compromise version of the work. The CSV plus the mapping plus the click-path
is the whole job, and doing the mapping up front is what makes the difference between a
database that filters, sorts and rolls up and a wall of Text columns.

Three things break in the same place without it. The import "fails" and gets abandoned
because every column is Text. The select columns come in empty because a CSV cannot carry
options. The relation columns look linked but are not, because the target database did not
exist yet.

## Who this is for

Any stage, any size. Useful when the workspace is not connected, when the user declines the
connection step, when an import has already gone wrong and only the property fixes are
needed, or when another skill produced a schema and the user wants to load it by hand.

**What it does not do:** decide your schema, create the database, connect anything, or
invent a value you did not supply.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message**
for only what is still missing, and reuses everything the module skill already confirmed.
Its opening question is:

> **Q:** Do you want an empty template or example rows?

Only then does it recommend the smallest workflow, and emits artifacts after you ask:

1. **Identify intent** - manual setup, CSV only, mapping only, or a fix for an import that
   already went wrong.
2. **Ask what is missing** - one question per message, never re-asking what you or the
   module skill already said.
3. **Recommend one approach** - one CSV, one mapping table, the import steps, and nothing
   else.
4. **Build only on request** - CSV, property mapping, import steps or a verification
   checklist, data only.

The intended workflow is: Field list confirmed → CSV exported → Database created → CSV
imported → Properties converted → Verified

## Example mapping

The shape of the mapping you get, illustrated on a tax register. These rows are
documentation examples: the real mapping uses the confirmed fields of the module you pick.

| CSV column | Notion property | After import |
|---|---|---|
| Tax Record | Title | Use as database title |
| Tax Type | Select | Add confirmed tax types |
| Tax Period | Text | Leave as Text |
| Tax Period Start | Date | Convert to Date |
| Tax Collected on Sales | Number | Set currency format |
| Net Tax Payable | Number | Set currency format |
| Tax Filing Due Date | Date | Convert to Date |
| Status | Select | Add confirmed statuses |
| Tax ID | Unique ID | Prefer automatic ID |

Property types map one way only. Money becomes a Number with a currency format, never Text
- and the currency is the one your business uses, never one this page picks for you. Dates
become Date. Checkbox, URL, email, phone, person, files and multi-select each have their own
Notion type, listed in full in the skill.

## Frequently asked questions

### Do I have to connect Notion for this?

No. That is the point of this skill. It produces text - a CSV, a mapping and steps - and you
do the import in Notion's own interface. If you would rather connect, the module skill owns
that build instead, and it asks before it starts.

### Why did every column import as Text?

Because a CSV has no types. Notion reads a header row and a list of strings, and every
column starts as Text by design. The import did not fail. Convert each column using the
mapping table, and the database behaves as intended.

### Can the helper decide which fields I need?

No, and it does not try. The field list belongs to the module that owns the process -
`leave-management` for leave, `tax-register` for tax - and this helper reformats that list
rather than inventing one. Ask which database you are preparing and it reads the confirmed
schema from that module.

### How do I handle a column that points at another database?

Import the database it points at first, then import this one, then convert the column to
Relation and pick the target by hand. A CSV import never creates a working relation on its
own, and pretending otherwise is the fastest way to a database full of broken links.

### Should I use Unique ID or keep the imported ID?

Use Unique ID where the module defines a prefix, and delete the imported column, or keep the
imported value as Text. Never mint IDs for real records: an ID that looks sequential but was
made up will collide with whatever the system assigns later.

### What does this system not do?

- It formats another module's schema. It never decides the schema and never creates the
  database.
- It performs no Notion action at all, so it can never claim one happened.
- Rollups, formulas, permissions, sharing and relations are configured by hand afterwards.
- Select options are a starting set to add after import, not your confirmed taxonomy.

### How does it fit with other systems?

It sits on top of them rather than beside them. Related modules:
`sme-ops-system-builder`, `people-directory`, `notification-reminder-hub`. The helper adds no
storage of its own, so replacing a module's schema changes the CSV and nothing else.

## Notion setup

Prefer the connected route? Every module skill asks for the connection first and, once you
reply that Notion is connected, creates the database and its properties for you.

Going it alone, which is what this helper is for:

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected, not a failure.
3. Apply the property mapping, one column at a time, in the order the skill gives:
   Title, dates, numbers, currency, select, status, IDs, relations.
4. Delete the example row if you asked for one, then verify against the checklist.

## Troubleshooting

- **Every column is Text** - expected. Apply the mapping table once, after import.
- **Select columns are empty** - a CSV cannot carry options. Add the confirmed values.
- **Dates sort alphabetically** - convert the column to Date; a Text column sorts as text.
- **A number will not total** - it is still Text. Convert it to Number and set the format.
- **A relation column is empty** - the target database has to exist first. Import it, then
  convert the column to Relation by hand.

**SOP & Company Wiki** - an SOP library records each recurring process once, with an owner and a review date, so people stop asking in chat. Instead of a spreadsheet only one person understands, each process becomes a row with a named owner, a status and a review rhythm. 12 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per process, 12 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 12 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `SOP Title`; `Category`; `Department`; `Description`.
- `Last Reviewed`; `Next Review`; `Owner`; `Priority`.
- Plus 4 more: `SOP ID`, `Status`, `Tags`, `Version`.

Field types break down as 1 auto ID, 5 text, 1 long text, 3 select and 2 date. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

The person who knows how something works is the only person who knows, and they are on leave.

That is the argument for SOP and company wiki: an SOP nobody opens is worse than none. Start from the process that causes the most rework, and keep it short enough to be read.

Three things break at once without it. Nobody can answer "show me every process we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per process fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A growth-tier system: worth adding once headcount or volume makes manual tracking unreliable.

**What it does not do:** version-control changes or notify readers when a process changes.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** Which process hurts most to run?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - write one page per process with owner, trigger and steps. Publish them where the team already works.
4. **Build only on request** - CSV, SQL DDL, JSON Schema and a Notion mapping, data only.

The intended workflow is: Trigger → Steps → Owner → Checklist → Review after each run

## SQL reference

```sql
CREATE TABLE sop_company_wiki (
  sop_title VARCHAR(255),
  category VARCHAR(100) NOT NULL,
  department VARCHAR(255),
  description TEXT,
  last_reviewed DATE NOT NULL,
  next_review DATE NOT NULL,
  owner VARCHAR(255),
  priority VARCHAR(100) NOT NULL,
  sop_id SERIAL PRIMARY KEY,
  status VARCHAR(100) NOT NULL,
  tags VARCHAR(255),
  version VARCHAR(255),
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_sop_company_wiki_status ON sop_company_wiki (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

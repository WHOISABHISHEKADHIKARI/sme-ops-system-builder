**Project-Based Performance** - a project performance review scores completed work against fixed measures, with a reason recorded so the next project improves. Instead of a spreadsheet only one person understands, each project review becomes a row with a named owner, a status and a review rhythm. 14 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per project review, 14 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 14 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Project Review Title`; `Employee Name`; `Project`; `Project Manager`.
- `Role on Project`; `Review Date`; `Delivery Score`; `Quality Score`.
- Plus 6 more: `Collaboration Score`, `Overall Score`, `Feedback`, `Linked Performance Review`, `Status`, `Project Review ID`.

Field types break down as 1 auto ID, 5 text, 1 long text, 1 select, 4 number, 1 date and 1 relation. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Project reviews are subjective and are not comparable between projects.

That is the argument for project-based performance: project performance needs a consistent denominator to be comparable. Fix the measures and the close reason, and the comparison works.

Three things break at once without it. Nobody can answer "show me every project review we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per project review fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is under an hour of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A scale-tier system: build it when the business already runs on its own data rather than around it.

**What it does not do:** assess individuals or report on company-wide performance.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How many live projects do you have?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - score a project at completion against three or four fixed measures, and keep a close reason code so the data improves over time.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Project delivered → Measures scored → Close reason recorded → Review across projects

## Frequently asked questions

### What is the difference between project-based performance and a spreadsheet?

A spreadsheet is a container. Project-Based Performance is a defined set of 14 fields, a known owner and a stated review rhythm, which is what makes the data trustworthy. The skill emits the same field list as CSV, SQL and JSON Schema so the structure survives the move out of the sheet.

### What fields does a project-based performance system usually include?

At minimum Project Review Title, Employee Name, Project, Project Manager. A complete version also covers Role on Project, Review Date, Delivery Score, Quality Score. This template ships all 14, with types fixed rather than guessed.

## SQL reference

```sql
CREATE TABLE project_based_performance (
  project_review_title VARCHAR(255),
  employee_name VARCHAR(255),
  project VARCHAR(255),
  project_manager VARCHAR(255),
  role_on_project VARCHAR(255),
  review_date DATE NOT NULL,
  delivery_score NUMERIC NOT NULL,
  quality_score NUMERIC NOT NULL,
  collaboration_score NUMERIC NOT NULL,
  overall_score NUMERIC NOT NULL,
  feedback TEXT,
  linked_performance_review VARCHAR(255),  -- relation -> target record
  status VARCHAR(100) NOT NULL,
  project_review_id SERIAL PRIMARY KEY,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_project_based_performance_status ON project_based_performance (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.

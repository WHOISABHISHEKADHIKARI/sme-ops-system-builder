**Projects & Work Management** - a work management register records each project and task with an owner, dates, dependencies and a status, so delivery is visible. Instead of a spreadsheet only one person understands, each project becomes a row with a named owner, a status and a review rhythm. 22 fields, emitted as CSV, SQL, JSON Schema and a Notion mapping from one source, so the four never disagree. This page covers what to track, why teams adopt it, what it costs, and a prompt you can paste straight in.

## What is this

Concretely it is a table, not a document: one row per project, 22 named columns, and the same field list emitted as four artifacts that cannot drift apart.

The 22 fields you would otherwise scatter across a sheet, a chat thread and someone’s memory:

- `Project Name`; `Actual Cost`; `Budget`; `Currency`.
- `Invoices`; `Client / Stakeholder`; `Client Account`; `Client Satisfaction Score`.
- Plus 14 more: `Deliverables`, `Department`, `End Date`, `Milestones`, `Notes`, `Priority` and 8 more.

Field types break down as 1 auto ID, 9 text, 1 long text, 3 select, 2 number, 2 currency, 2 date and 2 relation. Money stays numeric, dates stay dates, and anything that points at another table stays a relation, so the same field list can be emitted as CSV, SQL, JSON Schema or a Notion mapping without the four drifting apart.

## Why we need this

Delivery status is reported from memory at the weekly meeting.

That is the argument for projects and work management: two systems fail at the boundary. If tasks live in a tool, the register should hold only what the tool cannot: ownership, dates and health.

Three things break at once without it. Nobody can answer "show me every project we have" without checking with a person, the numbers get rebuilt by hand every period, and the person who built the sheet eventually leaves. A named record per project fixes the first, turns the second into a filter, and survives the third.

Adopting it early is cheap. The first version is a couple of hours of work, and no new software is needed, because it starts as a spreadsheet you already own.

## Who this is for

A starter-tier system: most small teams need it from day one.

**What it does not do:** schedule people, replace a project tool or manage dependencies automatically.

## How it works

The skill runs context first. It identifies the intent, asks **one question per message** for only what is still missing, and stops as soon as the remaining answers would not change the output. Its opening question is:

> **Q:** How are projects tracked right now?

Only then does it recommend the smallest workflow, and builds artifacts after you ask:

1. **Identify intent** - is this a new build, a fix, a review or advice?
2. **Ask what is missing** - one question per message, never re-asking anything you already said.
3. **Recommend one approach** - use the project tool people already update for tasks, and keep this as the register of projects, owners, dates and health.
4. **Build only on request** - CSV, SQL DDL, JSON Schema, a Notion mapping or an Excel workbook, data only.

The intended workflow is: Project created → Owner and dates → Tasks tracked → Status review → Closed

## SQL reference

```sql
CREATE TABLE projects_work_management (
  project_name VARCHAR(255),
  actual_cost NUMERIC(14,2) NOT NULL,
  budget NUMERIC(14,2) NOT NULL,
  currency VARCHAR(255),
  invoices VARCHAR(255),  -- relation -> target record
  client_stakeholder VARCHAR(255),
  client_account VARCHAR(255),  -- relation -> target record
  client_satisfaction_score NUMERIC NOT NULL,
  deliverables VARCHAR(255),
  department VARCHAR(255),
  end_date DATE NOT NULL,
  milestones VARCHAR(255),
  notes TEXT,
  priority VARCHAR(100) NOT NULL,
  progress NUMERIC NOT NULL,
  project_id SERIAL PRIMARY KEY,
  project_manager VARCHAR(255),
  project_type VARCHAR(100) NOT NULL,
  sprint VARCHAR(255),
  start_date DATE NOT NULL,
  status VARCHAR(100) NOT NULL,
  team_members VARCHAR(255),
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_projects_work_management_status ON projects_work_management (status);
```

## Notion setup

1. New page -> Import -> CSV, then pick the exported file.
2. Notion imports every column as Text. That is expected.
3. Apply the property mapping in the skill, one column at a time.
4. Delete the example row once real data is in.

## Troubleshooting

- **Columns show as Text after import** - expected. Apply the mapping table.
- **Relation column stays empty** - the target table has to exist first.
- **Dates sort as text** - convert the column to Date after import.
- **Numbers will not total** - the currency fields are numeric; do not reformat them as text.
